# Feasibility, evidence, and supported scope

Evidence reviewed 2026-11-16. Official Apple documentation describes APIs, not an executed physical-device result. Conclusions below distinguish source facts, engineering inference, implemented behavior, and unverified paths.

| Question | Evidence and conclusion |
| --- | --- |
| Does USB imply routing? | No implemented mechanism establishes that. Apple [External Accessory](https://developer.apple.com/documentation/externalaccessory) describes manufacturer-authorized accessory protocols. It is not evidence for an arbitrary iOS-test-to-Mac USB serial socket. MFi participation has separate [requirements](https://mfi.apple.com/en/faqs.html). No such API is used. |
| Development USB forwarding? | The primary [libusbmuxd project](https://github.com/libimobiledevice/libusbmuxd) documents `iproxy` forwarding a Mac TCP listener to a device port. It is third-party use of usbmuxd, not a general public Apple SDK transport contract. The direction does not directly provide this SDK's outbound iPhone-to-Mac channel. A reversed control architecture/device listener would need separate investigation. Library LGPL-2.1; utilities GPL-2.0. Nothing is linked, bundled, installed, or relied on. OS/device pairing changes would be a maintenance burden. **USB acceptance unresolved.** |
| Public IP alternative? | Apple [TN3151](https://developer.apple.com/documentation/technotes/tn3151-choosing-the-right-networking-api) recommends supported networking APIs. This implementation uses NWListener/NWConnection for Mac TCP services and URLSession for SDK control. It explicitly requires a reachable IP network, usually a trusted Wi-Fi LAN. An independently established wired IP route could also work but is unverified. |
| Local permission? | Apple [TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy) covers outgoing local TCP connections and privacy consent. The sample declares NSLocalNetworkUsageDescription. No Bonjour browsing or multicast entitlement is required by the direct-address design. Actual consent behavior still needs device validation. |
| HTTP fixture / ATS? | [NSAllowsLocalNetworking](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowslocalnetworking) describes local-resource ATS behavior and version differences. The sample declares intent with this key. This is separate from local-network privacy consent. If OS-specific ATS denial persists, use a narrowly scoped test-host exception for the exact origin, not a production-wide arbitrary-loads exemption. |
| Control survives failure? | By design, control goes directly to a separate listener, not through the relay. Only relay sockets are interrupted. A real device test must confirm endpoint routing and interface stability; an actual Wi-Fi outage would affect the IP control channel too. |
| Route the app? | Inject the Mac relay URL/port into the app's networking configuration. The agent has one fixed upstream selected locally. SDK installation alone changes no application URL or global proxy setting. This is not arbitrary-app compatibility. |
| HTTPS / validation? | Relay forwards opaque TCP bytes. [Apple server trust guidance](https://developer.apple.com/documentation/foundation/performing-manual-server-trust-authentication) leaves certificate and hostname checks with the client. Inference: changing an HTTPS URL to the Mac IP generally changes the validation hostname and can fail. Preserve a controlled test hostname/certificate with explicit test DNS routing if evaluating TLS; no DNS or certificate setup is automated here. Never disable trust checking. **Not integration-validated.** |
| Pinning? | Apple [identity pinning](https://developer.apple.com/news/?id=g9ejcf8y) describes stricter server identity checks. Inference: transparent byte forwarding need not change pinned keys, but endpoint/hostname and routing must still be valid. No MITM certificate, trust override, or pinning bypass exists. **Unverified.** |
| HTTP/2 and HTTP/3? | HTTP/2 over TCP is an unverified pass-through candidate, with all streams on one TCP connection sharing that connection's cap. HTTP/3 uses QUIC/UDP and is unsupported. The relay does not stop alternative endpoints or UDP traffic from bypassing it. Do not claim a conditioned test when an app silently takes an alternate path. |
| Background URLSession? | Apple's [background configuration](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/background(withidentifier:)) delegates transfer execution to a system process. The sample uses foreground ephemeral URLSession, with explicit restart recovery. Background scheduling, persistence, routing, and reconnection are **unverified**; a custom in-process hook would not establish coverage of system-owned transfers. |

## Native engine decision

The brief requested an evaluation of existing engines. [Toxiproxy](https://github.com/Shopify/toxiproxy) was evaluated as a TCP engine with an MIT license and directional per-connection toxics. The user subsequently explicitly excluded its use. No dependency was acquired or included. The product uses only the native Swift relay; there is no engine download at installation/runtime and no fallback to another engine.

The native scope is intentionally smaller than a packet conditioner. It paces byte writes, delays delivery of relay read chunks, and interrupts sockets. Rates affect existing loops and newly accepted relay sockets. They are per connection, not session-aggregate. Many simultaneous connections can exceed a single configured cap in aggregate. Protocol framing and TLS overhead count toward the cap. Delay applies to both directions; chunk size, backpressure and scheduling influence its end-to-end effect. It does not model a precise geographic RTT, jitter distribution, IP packet loss, retransmission, Wi-Fi association, RF attenuation, or radio interference.

`interrupt` cancels real controlled TCP connections; new TCP attempts are accepted and immediately closed while blocked. It does not promise a specific FIN versus RST observation on the phone; that is OS-dependent. TCP half-close is forwarded during normal operation. Buffers may deliver previously forwarded bytes after a command acknowledgement. Restore permits new streams and removes pacing; the example restarts the whole GET, validates length and hash, and never treats task cancellation as a network failure model.
